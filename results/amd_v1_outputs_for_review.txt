ID: ex003_fsm_wrong_transition
BUG CLASS: fsm_bug
--------------------------------------------------------------------------------
### Fixed RTL
module traffic_fsm (
    input logic clk,
    input logic rst,
    input logic tick,
    output logic green,
    output logic red
);
    typedef enum logic {S0, S1} state_t;
    state_t state, next_state;

    always_ff @(posedge clk or posedge rst) begin
        if (rst)
            state <= S0;
        else
            state <= next_state;
    end

    always_comb begin
        next_state = state;
        case (state)
            S0: if (tick) next_state = S1;
            S1: if (tick) next_state = S0; // Fix: Toggle from S1 back to S0
        endcase
    end

    always_comb begin
        green = 0;
        red = 0;
        case (state)
            S0: green = 1;
            S1: red = 1;
        endcase
    end
endmodule

### Bug Explanation
The bug occurs because when the system is in state S1, it does not transition back to state S0 even though tick is asserted. This means that once the system enters state S1, it will remain there indefinitely, causing the traffic light to be stuck in the red state. To correct this, the next_state should be set to S0 when the system is in state S1 and tick is asserted.

### Verification Suggestion
Test the traffic light controller for one cycle where tick is asserted while the system is in state S1. Verify that the system transitions back to state S0 on the next cycle.

ID: ex011_edge_detector_blocking
BUG CLASS: blocking_vs_nonblocking
--------------------------------------------------------------------------------
### Fixed RTL
module edge_detect (
    input logic clk,
    input logic rst,
    input logic sig,
    output logic pulse
);
    logic prev;

    always_ff @(posedge clk or posedge rst) begin
        if (rst) begin
            prev <= 1'b0;
            pulse <= 1'b0;
        end else begin
            prev <= sig;
            pulse <= sig & ~prev;
        end
    end
endmodule

### Bug Explanation
The bug arises because the `always_ff` block does not have sensitivity to the `sig` input. This means that the `pulse` output will never be updated based on changes in `sig`. The fix involves adding `sig` to the sensitivity list of the `always_ff` block.

### Verification Suggestion
Test the module with a sequence where `sig` transitions from 0 to 1 and then back to 0. Verify that `pulse` goes high for exactly one clock cycle during the first transition and remains low thereafter.

ID: ex015_alu_zero_flag_incomplete_comb
BUG CLASS: incomplete_combinational_logic
--------------------------------------------------------------------------------
### Fixed RTL
module alu8 (
    input logic [7:0] a,
    input logic [7:0] b,
    input logic [1:0] op,
    output logic [7:0] y,
    output logic zero
);
    always_comb begin
        case (op)
            2'b00: begin
                y = a + b;
                zero = (y == 8'd0);
            end
            2'b01: begin
                y = a - b;
                zero = (y == 8'd0);
            end
            2'b10: begin
                y = a & b;
                zero = (y == 8'd0);
            end
            2'b11: begin
                y = a | b;
                zero = (y == 8'd0);
            end
        endcase
    end
endmodule

### Bug Explanation
The bug occurs because the `zero` flag is only set for the bitwise AND operation. For addition, subtraction, and bitwise OR, the `zero` flag remains low even if the result is zero. This violates the design intent that `zero` should be high when the result is zero regardless of the operation performed.

### Verification Suggestion
Test the ALU with all possible combinations of inputs and operations, including cases where the result is zero. Specifically, check that the `zero` flag is high for both the bitwise AND and bitwise OR operations when the result is zero.

ID: ex021_reset_missing_data_reg
BUG CLASS: reset_logic
--------------------------------------------------------------------------------
### Fixed RTL
module valid_data_reg (
    input logic clk,
    input logic rst,
    input logic load,
    input logic [7:0] data_in,
    output logic [7:0] data_out,
    output logic valid_out
);
    always_ff @(posedge clk or posedge rst) begin
        if (rst)
            data_out <= 8'b0;
        else if (load) begin
            data_out <= data_in;
            valid_out <= 1'b1;
        end
    end

    always_ff @(posedge clk) begin
        if (!rst)
            valid_out <= 1'b0;
    end
endmodule

### Bug Explanation
The original design does not properly initialize `data_out` when `rst` is asserted. This can lead to undefined behavior for `data_out` until the first `clk` edge after reset. The fixed version ensures `data_out` is cleared on reset regardless of the state of `valid_out`.

### Verification Suggestion
Test the reset functionality by driving `rst` high, then low, and observe that `data_out` and `valid_out` are both zero. Then drive `load` high and verify `data_out` captures `data_in` and `valid_out` goes high on the following clock edge.

ID: ex025_counter_mod6_wrong_terminal
BUG CLASS: counter_width_boundary
--------------------------------------------------------------------------------
### Fixed RTL
module mod6_counter (
    input logic clk,
    input logic rst,
    input logic en,
    output logic [2:0] count
);
    always_ff @(posedge clk or posedge rst) begin
        if (rst)
            count <= 3'd0;
        else if (en) begin
            if (count == 3'd5)
                count <= 3'd0;
            else
                count <= count + 1'b1;
        end
    end
endmodule

### Bug Explanation
The bug occurs because the counter increments from 5 to 6 instead of wrapping around to 0. This happens because the comparison should be with 3'd5, not 3'd6. The modulo-6 operation requires the counter to wrap at 5, not 6.

### Verification Suggestion
Test the counter with en toggled on and off multiple times while observing the count output. Ensure it correctly counts from 0 to 5 and resets back to 0 upon re-enabling.

ID: ex027_uart_tx_fsm_data_to_stop
BUG CLASS: fsm_bug
--------------------------------------------------------------------------------
### Fixed RTL
module uart_tx_fsm (
    input logic clk,
    input logic rst,
    input logic start,
    input logic baud_tick,
    input logic [2:0] bit_index,
    output logic in_data,
    output logic in_stop
);
    typedef enum logic [1:0] {IDLE, START, DATA, STOP} state_t;
    state_t state, next_state;

    always_ff @(posedge clk or posedge rst) begin
        if (rst)
            state <= IDLE;
        else
            state <= next_state;
    end

    always_comb begin
        next_state = state;
        case (state)
            IDLE:  if (start) next_state = START;
            START: if (baud_tick) next_state = DATA;
            DATA:  if (baud_tick && bit_index == 3'd7) next_state = STOP;
            STOP:  if (baud_tick) next_state = IDLE;
        endcase
    end

    assign in_data = (state == DATA);
    assign in_stop = (state == STOP);
endmodule

### Bug Explanation
The bug occurs because when the FSM is in the STOP state and receives a baud_tick, it incorrectly transitions back to IDLE instead of remaining in STOP until the next bit_index condition is met. This violates the design intent that the STOP state should persist for one more baud period after sending all data bits.

### Verification Suggestion
Test the UART TX with a sequence where the last bit of the final byte is sent at the very edge of the last baud period. Verify that the STOP state persists for one full baud cycle before transitioning to IDLE.
